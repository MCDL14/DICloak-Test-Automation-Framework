# 创建使用自定义代理的环境并成功打开：设计说明

## 目标

在现有 P0【环境管理】用例组中增加一个自动化用例：创建名为 `测试自定义代理` 的环境，将代理设置为自定义代理，通过快捷输入解析 `http://192.168.20.33:7897`，保存环境并打开；打开后最多等待 100 秒，确认本次启动产生的 `GinsBrowser` 主进程存在。随后关闭环境并删除测试环境。

## 实现边界

- 正式用例放在 `tests/p0/environment_management/test_42_create_custom_proxy_environment.py`。
- 复用现有 `unittest`、`CDPDriver`、`LoginPage` 和 `EnvironmentPage` 结构。
- 自定义代理表单的定位、操作和状态读取集中补充到 `pages/environment_page.py`。
- 在正式代码落地前，先在系统临时目录建立一次性验证脚本，连接当前通过 CDP 启动的 DICloak，使用可用的 `http://127.0.0.1:7897` 验证真实页面的选择器与完整业务流程；临时脚本不进入 Git。正式用例仍使用 `http://192.168.20.33:7897`。
- 不实现代理连通性、代理地区、出口 IP、浏览器页面内容或其他未要求的验证。

## 页面对象设计

`EnvironmentPage` 增加细粒度能力，用于：

1. 读取【创建环境】按钮的可见及可用状态。
2. 打开创建环境抽屉并等待抽屉可见。
3. 填写并读取【环境名称】。
4. 将【代理设置】切换为【自定义代理】。
5. 读取【快捷输入】输入框和【解析】按钮的可见状态。
6. 填入快捷代理地址并点击【解析】。
7. 读取解析后的代理 IP 与端口字段。
8. 点击【确定】并等待创建环境抽屉关闭。

正式用例调用这些能力，页面对象不引入与本用例无关的通用环境配置模型。

## 流程与允许的验证

正式用例只针对需求中明确列出的预期结果进行验证：

1. 进入【环境管理】后，【创建环境】按钮可见且可用。
2. 点击按钮后，创建环境抽屉可见。
3. 填写后，环境名称字段的值为 `测试自定义代理`。
4. 选择【自定义代理】后，【快捷输入】和【解析】可见。
5. 解析后，IP 字段值为 `192.168.20.33`，端口字段值为 `7897`。
6. 保存后，抽屉关闭，环境列表中出现 `测试自定义代理`。
7. 点击该环境的【打开】后，最多等待 100 秒；检测到本次点击后新增的 `GinsBrowser` 主进程即通过。超时未检测到则令当前用例 Fail，测试运行器继续执行后续用例。
8. 成功打开后点击【关闭】，处理 DICloak 的关闭确认框，并等待环境关闭完成。
9. 环境关闭后删除 `测试自定义代理`。

不把环境操作按钮变为【关闭】作为额外业务断言；仅在关闭步骤中把按钮状态作为操作同步条件。用例不验证代理是否可联网。

## 进程判定

点击【打开】前记录配置中 `browser_process_name` 对应的主进程 PID 集合；点击后调用现有进程等待能力，最多等待 100 秒，要求出现新的主进程 PID。与只判断系统中是否存在任意 `GinsBrowser` 相比，这可以避免其他已打开环境的残留进程造成误通过，同时仍只服务于“本次环境成功启动且检测到进程”的预期结果。

## 清理与错误处理

关闭和删除属于用例主体步骤。用例仍在 `finally` 中保留异常情况下的尽力清理：

1. 若本次环境已经打开，尝试关闭并等待可删除状态。
2. 搜索并删除名为 `测试自定义代理` 的环境。
3. 清空列表搜索条件。

清理动作不作为测试断言。主体流程的原始失败应被保留，不由清理异常覆盖。运行前也会以相同名称进行幂等清理，避免上次异常退出留下的数据影响本次运行。

## 验证策略

1. 用一次性临时脚本连接当前 DICloak，逐步输出实际控件状态、解析字段值、列表结果和新进程 PID。
2. 临时脚本完整走通并完成清理后，再增加正式页面对象方法和测试文件。
3. 对新增的纯定位/解析脚本逻辑做最小化契约验证，并运行正式目标用例。
4. 最后运行与环境创建、打开和清理相关的现有测试或静态编译检查，确认没有引入回归。
